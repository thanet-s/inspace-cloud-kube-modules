## v1.1.5

### Deployment

- `deploy update` can now grow the control-plane servers in place. Raise
  `control_plane_vcpu` and/or `control_plane_memory_mib` in the inventory and
  run `update`. Before, a changed size was refused and the only path was a
  destroy and recreate. The resize runs one server at a time after the RKE2
  upgrade step: `update` requires every control-plane node Ready and etcd
  healthy, cordons the node, and journals the resize. It then stops the VM
  gracefully, changes its vCPU and memory while it is stopped, reads the new
  size back, and starts it. The stop is never forced. `update` moves on only
  after the host is on a new boot with a healthy local API and etcd, the node
  is Ready, and the private API answers. Each server is down for about three
  minutes. With three control planes etcd keeps quorum throughout. A single
  control plane is unavailable for the same period. Control planes can only
  grow; a smaller size is refused before anything changes.
- The resize is resumable. `state.json` records `controlPlaneResize` (the
  target, the server in progress, and the servers done) before each VM change,
  and `update` finishes an interrupted resize on the next run, before any RKE2
  upgrade and before it waits for the API, so a server left powered off is
  started first. `update` reads every control-plane VM before it journals
  anything and refuses if one is above the target or is not the journaled VM. When every
  server is done, `state.json` records `controlPlaneMachine`. `cluster.yaml`
  keeps its creation-time size, so ownership records and `destroy` stay valid,
  and `status`, `tunnel` and `destroy` keep working when the inventory differs
  from that size; only `update` refuses a shrink. A VM that already runs at the target size, for example one
  resized in the InSpace console, is not stopped; `update` verifies its node
  and records the size.
- `inspace-cluster-controller` gains `--resize-control-plane` (with `--slot`,
  `--vcpu`, `--memory-mib`, and `--expected-private-ipv4`) and a read-only
  `--resize-check`. The subcommand is idempotent and refuses a VM whose
  private address, UUID, or ownership record does not match the journaled
  cluster. After a resize, use `update`, not `init`.

### Client

- The InSpace client adds `StopVM`, `StartVM`, and `UpdateVMCompute`. A stop
  or start that times out is ambiguous, so callers read the VM status back.
  `UpdateVMCompute` verifies that the response shows the requested size.
