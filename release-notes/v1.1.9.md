## v1.1.9

### CCM: per-VM firewall limit

- InSpace drops every new outbound connection of a VM that has four or more
  firewalls attached, whatever the rule count. In production this cut a
  worker's kubelet off the API server when the CCM attached a fourth firewall
  (the base node firewall, two per-Service `public-node-local` firewalls and the
  new one).
- Before the CCM attaches any firewall to a VM (per-Service, shard or aggregate
  firewall, cluster ICMP firewall, make-before-break target) it reads the VM's
  firewalls back from the API, counts all of them and refuses an attachment that
  would exceed the limit. An already attached firewall does not add to the
  count. A failed readback also refuses the attachment and is retried.
- The limit defaults to 3. Set `ccm.nodeLoadBalancer.maxFirewallsPerVM` in the
  chart (`INSPACE_NODE_LOAD_BALANCER_MAX_FIREWALLS_PER_VM` in the standalone
  manifest); the CCM treats a value below 1 as 3.
- A refusal attaches nothing and keeps the existing exposure like any error
  that is not a verified intent. The node is not added for that Service, a
  `FirewallLimitExceeded` Warning Event on the Service names the VM, the
  current count and the limit, and the pass is retried with the capped backoff.
- Every firewall attach and detach, and its readback result, is logged at info
  level with the owner, VM UUID and firewall UUID.

### Chart and manifest

- The CCM ClusterRole now grants `get` on `events` besides `create`, `patch` and
  `update`. Without it the hold Event failed with `events ... is forbidden:
  cannot get resource "events"`.
