## First 1.0 stable release

v1.0.0 marks this project's first major-version release, promoted from
`v1.0.0-rc.2` after a full live E2E `all` run against an isolated InSpace
account. Its content is entirely the floating-IP resilience work merged since
v0.9.0; there are no breaking changes and no new required operator action.

## Bastion/control-plane recovery from a bad floating IP

InSpace's floating-IP pool has repeatedly handed a bastion or control-plane VM
an address with no working SSH/internet path -- see RELEASING.md's
"known open issue" for the full history. Unlike Karpenter-managed worker
nodes, which already self-heal through `BadFloatingIPStore` and
`FastRegistrationTimeoutController` (v0.9.0), bastion and control-plane VMs
are provisioned once by the bootstrap reconciler outside Karpenter's
lifecycle and had no equivalent recovery path. Three changes close that gap:

- The E2E harness (`test/e2e/`) retries a dropped SSH session during
  cloud-init waits, and destroys and retries the whole cluster once, after a
  cooldown, if `init` doesn't converge.
- `deploy/`'s real operator lifecycle gets the same cloud-init retry, plus an
  opt-in `INSPACE_DEPLOY_INIT_AUTO_RECOVER=true` for the same destroy-and-retry
  behavior, gated the same way `CONFIRM_CLUSTER_DESTROY` already gates a
  manual destroy.
- `inspace-cluster-controller --until-ready` now probes TCP/22 on every
  bastion/control-plane floating IP once the cluster reports Ready, and
  destroys and retries once automatically if one stays unreachable past
  `--floating-ip-reachability-timeout` (default 5m) -- on by default, for
  every caller, with no configuration required.

This was validated live during `v1.0.0-rc.2`'s promotion run: the bastion was
handed the exact same known-bad address from the original investigation
months earlier, and the destroy-and-retry mitigation recovered automatically
with zero manual intervention.

None of this can reject a specific address up front -- InSpace's VM-create API
has no field for it -- so this remains detection and fast recovery, not
prevention. See `modules/cloud-provider/README.md` and `deploy/README.md` for
the new flags, and RELEASING.md for what a true fix would require.

## Upgrade notes

No schema, CRD, or immutable bootstrap changes. Existing clusters are
unaffected by upgrading `modules_version` to `1.0.0`; the new reachability
guard and auto-recover flag only affect a subsequent `init`/`--until-ready`
run, not an already-running cluster.
