## RKE2 1.36 and Karpenter 1.14.1

v0.9.0 upgrades the managed control plane to RKE2 1.36 and the vendored
Karpenter core to 1.14.1, and disables RKE2's built-in ingress add-ons (this
project already expects an operator-chosen ingress path). The immutable
bootstrap cache inventory is refreshed to match.

## Elastic workers recover faster from a bad floating IP

InSpace floating IPv4 addresses come from a shared, reused pool, and some come
up with no working internet egress. Three changes together cut the cost of
hitting one:

- A new `inspace-wait-for-internet` bootstrap step pings out with a bounded
  5-minute deadline before package installation, so a broken address fails
  fast and visibly instead of retrying silently inside opaque `apt-get`
  errors.
- `FastRegistrationTimeoutController` shortens Karpenter's own 15-minute
  registration-liveness timeout to 9 minutes for any `InSpaceNodeClass` with
  `rke2.skipOSUpgrade: true` — safe only because that flag also removes
  cloud-init's own up-to-10-minute package-preparation budget from a healthy
  boot. NodeClasses that keep the OS upgrade (the documented production
  default) keep the stock 15-minute timeout.
- A new `inspace-bad-floating-ips` cache remembers, for 30 days, any address a
  NodeClaim was deleted on before ever registering. A later `Create()` handed
  that exact address deletes the VM and retries immediately instead of
  waiting for the guest to fail its own connectivity check again.

Both the cache and the faster timeout are best-effort speed optimizations, not
safety mechanisms: a store error is always treated as "not known bad" and
never blocks node provisioning. See `modules/karpenter-provider/README.md`'s
"Known-bad floating IP cache" section for the full mechanism. `SchemaVersion`
bumps to v13 since generated bootstrap semantics changed for an unchanged
`InSpaceNodeClass` spec.

## In-place RKE2 control-plane version upgrades

`deploy/run.sh update` can now upgrade the RKE2 binary on each fixed
control-plane server one at a time — stop, verify checksum, replace, restart,
wait for Ready and API recovery — before applying the operator RKE2 config
fragment, whenever the inventory's `rke2_version` differs from what the
cluster currently reports. The upgrade always fetches the target release
directly from upstream, since the bastion bootstrap cache pins exactly one
audited RKE2 version per controller build.

A downgrade or a jump of more than one minor version is refused unless the
operator exports `INSPACE_CONFIRM_RKE2_VERSION_SKIP=<cluster-name>`, matching
this project's other typed-confirmation gates. Elastic Karpenter workers
already converge to a new RKE2 version automatically through existing
NodeClass drift detection, so this closes the one gap `deploy/README.md`
previously listed under "not an in-place operation." See that file for the
cached-vs-direct-download coupling and the confirmation override.

## Other changes

- Added `CODE_OF_CONDUCT.md`, GitHub issue/PR templates, and a
  local-evaluation-only path in `README.md`, for reuse as a standalone
  open-source project.
- Refreshed pinned RKE2 bootstrap cache image digests and checksums, and
  picked up upstream gRPC security fixes.

## Upgrade notes

The faster-registration-timeout change touches generated worker bootstrap
semantics, so `SchemaVersion` bumps to v13; existing elastic workers converge
to it automatically through Karpenter's own NodeClass drift replacement, no
operator action required. Fixed control-plane and bastion VMs are unaffected
by that bump. Set `modules_version: 0.9.0` in the selected inventory before
running `deploy/run.sh update`, and see the RKE2 1.36 upstream release notes
before upgrading an existing cluster's `rke2_version`.
