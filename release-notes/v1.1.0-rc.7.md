## Security and supply-chain hardening

`v1.1.0-rc.7` builds on `v1.1.0-rc.6` and is the release candidate for
`v1.1.0`.

### Separate RKE2 agent token

- New clusters get a separate random RKE2 agent token. Every control plane
  sets `agent-token`, and Karpenter and Node-LB workers receive only that
  token. Before, workers received the server token, so root on any worker
  could fetch the cluster's bootstrap data (CA and etcd keys).
- The bootstrap controller reads it only from `INSPACE_RKE2_AGENT_TOKEN` and
  rejects a value equal to the server token.
- Existing clusters render byte-identical cloud-init and keep working.
  `deploy/README.md` ("RKE2 join tokens") describes how to add or rotate the
  agent token on an existing cluster.

### No credentials on command lines

- The InSpace API token Secret is created from a temporary 0600 file, not
  `--from-literal`, in deploy `init`/`update` and the E2E. Live scripts send
  the `apikey` header on stdin. Static checks forbid both patterns.

### Image and dependency pinning

- The published workload chart pins all three controller images by digest.
  The release job reads the chart back and fails unless every controller
  renders as `repo@sha256:`.
- Deploy resolves the release's recorded image digests anonymously, verifies
  them against the immutable release and GHCR, and runs the controller by
  digest. Clusters that use the bootstrap cache install by the linux/amd64
  digest the cache stores.
- Every module and E2E Dockerfile base image is pinned by digest, and the
  deploy and E2E Python dependencies install with `--require-hashes`.

### `deploy update` refreshes the bootstrap cache

- On clusters that use the bastion bootstrap cache, `update` first adds the
  target release's missing images and RKE2 archive to the cache, verified by
  digest and never overwriting an entry. Before, module upgrades and RKE2
  upgrades failed to pull on cached clusters.
- Cache maintenance no longer deletes RKE2 releases added after the bastion
  was built.
- New controller flag: `--print-bootstrap-cache-refresh`.

### E2E

- The service-cloud verifier accepts the private-local L2 Service identity
  that `v1.1.0-rc.6` added to the ownership journal. The `v1.1.0-rc.6` E2E
  failed because the verifier required exactly two private identities.

## Upgrade notes

- The deploy runner needs anonymous HTTPS access to `api.github.com`,
  `github.com`, and `ghcr.io` to verify release image digests.
- A cached cluster can be updated only to a release that includes the cache
  refresh.
