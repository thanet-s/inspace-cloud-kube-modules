## Build each cluster once: probe only the bastion floating IP

`v1.1.0-rc.4` builds on `v1.1.0-rc.3` (Ubuntu 26.04 default, bash login
shell, online CSI expansion, 2000 GiB CSI cap).

### Fixed: every healthy cluster was destroyed and rebuilt once

Since `v1.0.0`, `inspace-cluster-controller --until-ready` probed TCP/22 on the
bastion and every control-plane floating IPv4 once the cluster reported Ready.
The managed node firewall admits inbound traffic only from the private subnet
and pod CIDR, so a healthy control-plane address never answers from outside.
The probe therefore always failed, and every `init` (E2E and `deploy/`):

1. waited the full `--floating-ip-reachability-timeout` (5 minutes),
2. destroyed the healthy cluster and built it again,
3. waited another 5 minutes before giving up on the probe.

That cost about 22 minutes and one throwaway cluster per `init`, and it could
not tell a bad control-plane address from a good one.

- The controller now probes only the bastion floating IPv4, the one address
  whose firewall admits SSH from the management client. A sustained-unreachable
  bastion address still triggers the single destroy-and-retry.
- `test/e2e` and `deploy/` init now prove each control plane's internet egress
  from inside, through the bastion, before the long cloud-init wait. A fresh
  address gets up to 5 minutes. A bad control-plane floating IPv4 then fails
  `init` with the task
  "Prove every control plane reaches the internet through its floating IP" and
  reaches the existing destroy-and-retry path (`INSPACE_DEPLOY_INIT_AUTO_RECOVER`
  for `deploy/`).

## Upgrade notes

No API, CRD, chart, or cloud-init change. Existing clusters are unaffected.
