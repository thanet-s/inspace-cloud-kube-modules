## v1.1.8

### CCM: `public-node-local` load balancers fail static

- A `public-node-local` Service now keeps its last known good exposure on
  every error that is not a verified intent: an InSpace API error, an ambiguous
  firewall readback, an invalid annotation, a VM audit failure or datapath
  drift. It keeps the firewall assignments, the `inlb-dp-*` VIPs and the
  parent status, emits an Event and retries. In v1.1.7 any definite error, and
  any change to the set of published nodes, withdrew the whole Service.
- The exposure is withdrawn only on verified intent: the Service is deleted or
  leaves the mode, a Node or VM is proven gone, a node is excluded
  (`node.kubernetes.io/exclude-from-external-load-balancers`, control-plane
  role, a NodeClass without the public profile, a foreign billing account or a
  VM that no longer matches the providerID), or the explicit rebuild
  annotation below is set.
- Nodes are added and removed one at a time on a published Service. A new node
  gets its firewall, VIP and floating IP while the others keep serving; a
  removed node is detached and pruned alone. A node without a ready endpoint is
  removed after 60 seconds only while another node still serves; when no node
  has an endpoint, every node is kept.
- Changing `service.inspace.cloud/node-lb-pool` or the firewall policy (ports
  or `loadBalancerSourceRanges`, wider, narrower or mixed) is applied in place
  on the same Service, make-before-break. The target pool or a second firewall
  is brought up next to the active one, the parent status keeps the union
  while both serve, and the old side is detached only after the target is
  published and read back. A restart at any step resumes or rolls back without
  a pass where the Service has no address.
- A port claim stays with the Service that serves it, attributed by the pools
  of every node that still carries its VIPs. A newcomer with a lower UID no
  longer takes a serving Service's port, and a draining pool stays claimed
  until its last VIP is gone.
- A lost `inlb-dp-*` child is rebuilt in place from the recorded active ports
  (`service.inspace.cloud/public-node-local-active-ports`), including named
  target ports, and every kept node gets its VIP back first.
- `service.inspace.cloud/node-lb-allow-rebuild` allows the old withdraw and
  rebuild for one pending change. Any value is honoured once; removing the
  annotation before the first detach is read back cancels it. See the chart
  README runbook.
- The VM firewall audit fails only the affected node and Service. One
  Service's imperfect firewall no longer fails every Service on the VM.
- Firewall relation waits are bounded. The assignment timeout outlives the
  5m30s retire delay, pending waits requeue after a fixed delay, backoff is
  capped at 60 seconds, and a relation that never converges is parked for 30
  minutes per relation so other changes go ahead.

### CCM: standard public NLB

- Target updates add new targets before removing stale ones, and the last
  serving target is never removed because the desired set came up empty. An
  empty set is held for 15 minutes, then only targets whose VM is proven gone
  are removed.
- Dropping the public label or annotation keeps the NLB and its floating IP.
  They are released when the Service is deleted, or when
  `inspace.cloud/release-public-load-balancer` is set to an RFC3339 time later
  than the recorded drop. A held NLB keeps following its targets and rules.
- Each mutation has its own deadline (create NLB 5m, assign floating IP 3m,
  delete 3m, target or rule 2m, create floating IP 90s). An ambiguous receipt
  retires after its deadline plus 30 seconds and two spaced absent reads, then
  replays; a create may be re-staged once and a late create is adopted, so no
  duplicate paid resource is made. A failed add no longer blocks removals or
  rule updates.

### CCM: node lifecycle

- A VM is declared gone only on positive evidence: an empty VM inventory or
  empty VPC membership needs a second absent read at least 30 seconds later.
  At most half of the nodes can be declared gone per five minutes
  (`MassNodeAbsenceRefused`).
- A VM answer without a private IPv4 address keeps the Node's last addresses,
  and an empty floating-IP answer keeps the ExternalIP for five minutes.

### CCM: node load balancer NodePools

- The NodePools the CCM renders for node load balancers use
  `expireAfter: Never` and a disruption budget of `nodes: "0"`. These nodes own
  a public floating IP, and replacing one changed the address. Existing
  NodeClaims keep the `expireAfter` they were created with; the new NodePool
  hash marks them drifted, but the zero budget blocks the replacement.

### Chart and manifest

- The CCM Deployment spreads its replicas across nodes with required
  anti-affinity, declares port 10258, adds an https `/healthz` liveness probe,
  a PodDisruptionBudget with `maxUnavailable: 1` and a `maxSurge: 0`,
  `maxUnavailable: 1` rollout. The standalone manifest gets the same settings.
