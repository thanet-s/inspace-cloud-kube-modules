## Online CSI volume expansion

`v1.1.0-rc.1` lets a `ReadWriteOnce` PVC grow. Raise the PVC's
`spec.resources.requests.storage`, and the CSI driver grows the InSpace disk
and then its ext4 filesystem.

InSpace resizes a disk only through its VM attachment
(`PATCH /v1/{location}/user-resource/vm/storage`), so expansion is online-only.
If no Pod uses the PVC, `ControllerExpandVolume` returns `FailedPrecondition`
and `csi-resizer` retries until a Pod mounts the volume again. Shrinking is not
supported.

- The shared client adds `ResizeAttachedDisk`. It sends an absolute size and
  rejects a response for another disk or a smaller size.
- The controller resizes only an owned CSI `EMPTY` disk that is attached to
  exactly one VM in the configured VPC, never a VM boot disk. It refuses while
  an attach, detach, or delete Lease for the disk is unresolved, keeps the
  480-second dispatch reserve, and confirms the new size by exact disk readback.
- The node waits up to 30 seconds for the guest to see the larger virtio device,
  then runs `resize2fs` on the mounted filesystem.
- The chart and standalone manifests add the `csi-resizer` `v1.13.2` sidecar
  with a 600-second RPC timeout. The bootstrap cache pins its linux/amd64
  digest, so the audited inventory grows to 36 images (33 in the E2E cluster).
- `csi.storageClass.allowVolumeExpansion` defaults to `true`.

## Upgrade notes

Apply the workload chart from this candidate to add the resizer sidecar and
set `allowVolumeExpansion: true` on the chart-managed StorageClass. Kubernetes
allows that field to change in place, so existing PVCs can grow after the
upgrade.
