## v1.1.10

### CCM and chart: one firewall per VM for `public-node-local`

- New opt-in mode `ccm.nodeLoadBalancer.publicNodeLocal.firewallMode: perVM`
  (`INSPACE_NODE_LOAD_BALANCER_LOCAL_FIREWALL_MODE`). One firewall per
  `public-node-local` VM, named `inlb-<cluster>-vm-<VM UUID>`, holds the rules
  of every Service published on that VM. A VM stays at the base firewall plus
  one, so it can serve more than two Services under InSpace's limit of three
  firewalls. A ledger in an anchor ConfigMap `inlb-vmfw-<VM UUID>` in the CCM
  namespace records what the firewall holds and any step in flight.
- **Default off.** `firewallMode` defaults to `perService`, which behaves as in
  v1.1.9 when no per-VM state exists.
- **Migration is manual by default.** `vmFirewallMigration: manual` migrates a
  VM only when its Node has
  `service.inspace.cloud/public-node-local-vm-firewall-migrate: "true"`;
  `auto` migrates every VM. The Node annotation value `hold` pauses a VM in
  both modes and both directions. VMs migrate one at a time with a pause of four
  settle periods between them.
- A VM with a free slot gets the per-VM firewall created, attached and read
  back, then its per-Service firewalls detached. A VM that already carries three
  firewalls is migrated by adoption: one PUT renames a single-VM per-Service
  firewall (through `display_name`) into the per-VM firewall with the union of
  rules. The count never exceeds the limit and every live port stays covered
  after every call.
- Turning the mode back to `perService` runs the reverse migration per VM, one
  at a time, with the same guarantees. A VM that serves three or more Services
  can not go back and is refused with an Event.
- `vmFirewallSettleSeconds` (default `10`, range 10-600) is the wait after new
  rules are written. A live test on 2026-10-29 measured about 1 s for rules to
  take effect and no effect on established flows or on rules that did not
  change. A removed or narrowed rule stalls an established flow at once, so
  every step adds the new rule before it removes the old one.
- The chart and the standalone manifest always set `INSPACE_CCM_NAMESPACE` and a
  namespaced ConfigMap `Role` and `RoleBinding`, in every mode. The reverse
  migration runs with the mode off and needs both. The chart values schema
  validates the three new values.
- The chart README has the runbook: enable, migrate one VM, hold, roll back and
  clean up after an accidental downgrade.

### Rollback

1. If the CCM misbehaves, scale it to 0. The datapath keeps serving without it.
2. To abandon the feature, set `firewallMode: perService` on this release and
   wait for the reverse migration to finish: no `inlb-vmfw-*` ConfigMap and no
   per-VM firewall is left. Only then downgrade.
3. If a third Service shares a VM, first move its traffic back and delete that
   Service so its entry leaves the firewall, then do step 2.

Do not downgrade the CCM below this release while per-VM state exists. v1.1.9
on migrated state keeps serving: it never detaches or deletes a per-VM
firewall, never removes status or VIPs and never goes above three firewalls on
a VM. It is not frozen, though: after one hold Event it creates a per-Service
firewall for each Service and attaches it wherever there is room, and a
Service whose firewall could not be attached holds forever. Clean-up after such
a downgrade is in the chart README. Karpenter must be on this release before
`perVM` is enabled and must not be downgraded while a per-VM firewall exists.

### Karpenter and CCM: per-VM `public-node-local` firewall identity

- Karpenter now accepts one firewall named `inlb-<cluster>-vm-<VM UUID>` on a
  `public-node-local` VM, besides the base firewall and the per-Service
  firewalls. It must belong to this cluster and billing account, carry only
  canonical inbound TCP/UDP port rules, and be assigned to that VM only. Another
  VM's per-VM firewall, a second per-VM firewall, a foreign cluster or billing
  account, and an unexpected description are rejected as an ownership mismatch.
- The CCM recognises the same firewall. While the per-VM firewall mode is not
  enabled, a Service that finds its own VM's per-VM firewall holds: it keeps its
  status and VIPs, never detaches, deletes or attaches anything, and records a
  `PublicNodeLocalPerVMStatePresent` Warning Event. A per-VM-named firewall that
  is attached to a different VM is still rejected as an unauthorized additional
  firewall.

### Client: firewall rename

- `UpdateFirewall` now sends the name as `display_name`. InSpace ignored the
  `name` field of a firewall PUT (HTTP 200, no change), so a rename never took
  effect. The description is still sent but InSpace does not store it; the CCM
  and Karpenter already accept an empty description on a firewall they own.

### Tests

- The e2e verifier checks the per-VM firewall, its anchor and the Service
  annotations (`--firewall-mode perVM`). A new long-lived TCP probe holds one
  connection through the changes. The e2e adds, changes and removes Services on
  one edge VM under both probes and then proves the reverse migration.
- A test proves what v1.1.9 does on migrated state (see Rollback).
- Any `-race` run of `pkg/cloudprovider` needs `-timeout 60m`
  (`make -C modules/cloud-provider test-race`); `make e2e-static` checks it.
