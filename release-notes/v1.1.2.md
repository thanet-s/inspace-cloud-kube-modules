## v1.1.2

### Deploy

- `deploy/run.sh update` and `destroy` now end the deployment journal
  (`state.json`) with a real newline. Before, the file ended with the two
  characters backslash and `n` after the closing `}`, and the next `update`
  failed while loading it with `from_json failed: Extra data`. If you have
  an affected journal, open `state.json` and replace those last two
  characters with a newline, then run `update` again.

### Storage

- The CSI controller now runs volume attach and detach for one VM one at a
  time. InSpace accepts only one attach or detach request per VM while it is
  busy, so several PVCs attached to the same worker at once used to fail and
  leave mutation-fence Leases that kept the VolumeAttachments stuck. Attaches
  to different VMs still run in parallel.
- The `InSpace API is temporarily unavailable` error on a VolumeAttachment or
  PVC event now ends with the reason the cloud gave, for example the HTTP
  status and message of the failed request.
- Volume expansion takes the same per-VM turn, so a resize never overlaps an
  attach or detach on the same VM. A request that has less than its dispatch
  reserve left after waiting for the VM now fails at once with a retryable
  error, before it creates a fence, and the sidecar retries it.
- Upgrading does not clear mutation-fence Leases that an earlier version
  stranded. Look in the `kube-system` namespace for Leases labelled
  `storage.inspace.cloud/mutation-fence=true`. For each one, read the fence
  intent and check the disk in the InSpace console or API. Delete the Lease
  only after you confirm the cloud state: for an attach, the disk is not
  attached to the `desiredVMUUID`; for a detach, the disk is still attached
  because the detach never happened.
