## v1.1.3

### Deploy

- `deploy/run.sh init` now reboots the bastion and every control plane once
  after the first-boot OS upgrade, so the upgraded kernel and libc take
  effect. Before, they kept running the old kernel until someone rebooted
  them by hand. Control planes reboot one at a time, each only after every
  control-plane node is Ready and etcd reports healthy. The bastion reboots
  last, and `init` stops and restarts the API tunnel around it. After a
  reboot of a cached bastion, `init` waits for the bootstrap cache to answer
  before it goes on.
- `init` records each reboot on the host and skips a host that has already
  rebooted since cloud-init ran, so a repeated `init` does not reboot a host
  twice. `update` never runs `apt-get upgrade` and never reboots anything.
- The reboot is skipped when `skip_os_upgrade: true`. A new inventory option,
  `post_upgrade_reboot` (default `true`), turns it off while the OS upgrade
  still runs.
- Re-running `init` on a cluster that an older release created reboots, one at
  a time, every bastion or control-plane host that has not rebooted since it
  was created. Set `post_upgrade_reboot: false` in the inventory before you
  re-run `init` if you do not want that.

### Karpenter

- A worker whose NodeClass runs the OS upgrade (`spec.rke2.skipOSUpgrade`
  unset or `false`) now reboots itself exactly once after it registers with
  the cluster. The node waits up to 30 minutes for the `karpenter.sh/registered`
  label, writes a marker file, and then reboots, so a node never reboots twice
  and a node that never registers is not rebooted. A NodeClass with
  `skipOSUpgrade: true` does not reboot.
- The change applies only to workers created after you upgrade the provider.
  The bootstrap schema version is unchanged, so Karpenter does not treat
  running workers as drifted and does not replace them. Workers that already
  run keep their current kernel until Karpenter replaces them.
