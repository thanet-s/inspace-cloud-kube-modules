## v1.1.3

### Deploy

- `deploy/run.sh init` now reboots the bastion and each control plane that has
  a pending reboot (`/run/reboot-required`) after the first-boot OS upgrade, so
  the upgraded kernel and libc take effect. Before, they kept running the old
  kernel until someone rebooted them by hand. Control planes reboot one at a
  time, each only after every control-plane node is Ready and etcd reports
  healthy, and `init` waits for each node to be Ready and the API to answer
  before it moves on. Calls through the API tunnel are retried, so a VIP move
  does not fail `init`. The bastion reboots last, and `init` stops and
  restarts the API tunnel around it. After a reboot of a cached bastion,
  `init` waits for the bootstrap cache to answer.
- A host without `/run/reboot-required` is not rebooted. `init` records each
  reboot on the host, so a repeated `init` does not reboot a host twice.
  `update` never runs `apt-get upgrade` and never reboots anything.
- The reboot is skipped when `skip_os_upgrade: true`. A new inventory option,
  `post_upgrade_reboot` (default `true`), turns it off while the OS upgrade
  still runs.
- Re-running `init` on a cluster that an older release created reboots, one at
  a time, any bastion or control-plane host that has a pending reboot. Set
  `post_upgrade_reboot: false` in the inventory before you re-run `init` if you
  do not want that.

### Karpenter

- A worker whose NodeClass runs the OS upgrade (`spec.rke2.skipOSUpgrade`
  unset or `false`) now reboots once before it joins the cluster, when the
  upgrade left `/run/reboot-required`. The reboot comes before the node
  registers on purpose: Karpenter binds pending pods the moment a node
  registers, so a reboot after joining would restart the workload that caused
  the scale-up. The node finishes its setup, writes a marker file, reboots, and
  starts the RKE2 agent on the next boot. If that start fails, the node never
  registers and Karpenter replaces it, as for any failed start. A NodeClass
  with `skipOSUpgrade: true` does not reboot.
- The change applies only to workers created after you upgrade the provider.
  The bootstrap schema version is unchanged, so Karpenter does not treat
  running workers as drifted and does not replace them. Workers that already
  run keep their current kernel until Karpenter replaces them.
- A NodeClaim whose VM never registered (the registration TTL expired) no
  longer lingers for about 18 minutes after it is deleted. The VM and its
  floating IP were already gone within about three minutes, but every cleanup
  pass proved their absence again from scratch, with three reads 30 seconds
  apart for each stage. Deletion of a VM that is already missing now proves the
  VM absent once and then confirms it with one more read instead of running the
  same proof four times. A floating IP whose DELETE the NodeClaim's durable
  removal journal already records as observed needs one confirming read, not a
  second spaced proof. When provider Delete finishes the whole cleanup (VM,
  floating IP and base-firewall relation proven absent), it now records that in
  the NodeClaim's create-fence annotation, bound to the exact VM UUID, floating
  IP name and address, and firewall UUID. After Karpenter releases the
  NodeClaim, the create-protection controller then skips the destructive VM
  delete replay and runs only the read-only final audit, with two snapshots 10
  seconds apart instead of three 30 seconds apart. That audit still reads the
  exact VM, the floating IP and the firewall relation. If it finds any of them
  again, the controller falls back to the full cleanup, which deletes what
  reappeared through the normal authorized path and repeats the three-snapshot
  audit. Claims without a matching marker, attempts whose VM create was issued
  but never observed, and attempts that still track a dependent resource keep
  the full cleanup and the three-snapshot audit.
- Karpenter normally calls the provider's Delete a second time, because the
  fence writes made during the first call change the NodeClaim and make
  Karpenter's own update conflict. When the marker already matches the exact VM,
  floating IP and firewall, that repeat call now returns after one exact VM
  read that answers 404 instead of running the missing-VM cleanup again. Any
  other answer, including the VM being present, a server error or a timeout,
  runs the full delete.
- Deleting a live VM no longer repeats the VM-absence proof it just made. The
  three reads after the VM DELETE stay, but the floating-IP removal step and
  the firewall detachment each reuse that proof with one confirming read. If
  that read sees the VM, or fails, the check is no longer satisfied by a later
  single absent read: it then needs three spaced absent reads, like the full
  proof. The floating IP's own absence proof and the firewall relation's
  absence readback are unchanged.
- With these changes a never-registered claim's simulated cleanup at production
  intervals falls from 14 minutes to about 3 minutes 10 seconds.
- The create-protection controller now logs, at info level, why a cleanup is
  pending each time it requeues (waiting for Karpenter termination, a pending
  audit result, an unresolved protection step). Before, these waits returned no
  error and left no log line. VM deletion also logs each absence-proof stage at
  debug level.
