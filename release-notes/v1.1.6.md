## v1.1.6

### RKE2

- The audited RKE2 release moves from the release candidate
  `v1.36.5-rc2+rke2r1` to the GA release `v1.36.5+rke2r1` (Kubernetes 1.36.5).
  The bundled Cilium is unchanged: rke2-cilium 1.20.200 with Cilium 1.20.2.
  The bootstrap cache serves the GA RKE2 archive and `rke2-runtime` image, and
  the control-plane bootstrap, the examples, and the E2E templates pin
  `v1.36.5+rke2r1`. All other cached RKE2 images are the same as before.
- The release candidate is no longer accepted as the RKE2 version of anything
  new. The `rke2.version` checks of the `InSpaceCluster` and `InSpaceNodeClass`
  CRDs and validators and of the controller bootstrap, and `deploy init` and
  `deploy update`, now take exact GA releases only. A NodeClass that still
  names `v1.36.5-rc2+rke2r1` becomes NotReady: Karpenter launches nothing from
  it until it names a GA release. Workers that already run keep running.
- A cluster created on `v1.36.5-rc2+rke2r1` keeps working until it moves. Its
  `cluster.yaml` and `state.json` still name the candidate, and `deploy status`,
  `tunnel`, and `destroy` accept it, both with the inventory on the candidate
  and with the inventory already on `v1.36.5+rke2r1`, so an interrupted
  `update` does not lock them out. The control-plane resize of `deploy update`
  and `destroy` validate that persisted spec and accept the candidate too.

### Upgrading from `v1.36.5-rc2+rke2r1`

- A cluster created on `v1.36.5-rc2+rke2r1` upgrades with `deploy update`.
  Set `rke2_version: v1.36.5+rke2r1` in the inventory and run `update`. It is
  an ordinary RKE2 upgrade: the control-plane servers roll one at a time, and
  `update` still accepts the candidate as the version it upgrades from. The
  kubelet of the candidate already reports `v1.36.5+rke2r1`, so the journaled
  version in `state.json` is what records the move.
- `deploy update` moves the default NodeClass to the new release. Move every
  NodeClass that you created yourself and that still names
  `v1.36.5-rc2+rke2r1`: set `spec.rke2.version` to `v1.36.5+rke2r1`. Until
  you do, that NodeClass is NotReady and Karpenter does not launch workers from
  it. Workers that already run from it keep running.
- Changing `spec.rke2.version` of a NodeClass changes its `NodeClassHash`.
  Karpenter then marks every worker of that NodeClass Drifted, and replaces the
  workers under each NodePool's disruption budget. This covers the default
  NodeClass that `update` moves and the NodeClass of the CCM Node-LB pools.
  A NodePool with a `nodes: "0"` budget keeps running the
  `v1.36.5-rc2+rke2r1` agent until you replace its nodes in a maintenance
  window with `kubectl delete nodeclaim`, as described in `deploy/README.md`.
  The Node-LB pools replace their node automatically, so expect a short
  interruption on the public IP of that shard.
